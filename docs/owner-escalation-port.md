# Перенос механики chef-bot в Лею

Источник: https://github.com/bizgenieyg/chef-bot, ревизия a0d9026. Изучены index.js, services/db.js, natalia.js, learnedAnswers.js, nataliaReplyFormatter.js, jerusalemTime.js, reminders.js, prompts/support.js и sales.js. Локальная копия для исследования: /tmp/leya-chef-bot. Код и персональные настройки источника не переносились.

## Что найдено в chef-bot

- Модель помечает неизвестный вопрос ASK_NATALIA. Клиент получает обещание уточнить, владелец — отдельное сообщение с вопросом. SQLite escalations хранит клиентский chat ID, вопрос, сообщение владельцу и состояние queued/pending/answered.
- Ответ принимается только реплеем: payload.replyTo.id сопоставляется с сохранённым ID отправленного вопроса. В GOWS нужен короткий ID из _data.Info.ID, а не только составной true_chat_id. После отправки клиенту обращение помечается answered.
- Gemini отличает ANSWER от DEFER. Отсрочка переносит вопрос на следующие 09:00; после третьей отсрочки остаётся на ручной разбор. В источнике есть исключение: если клиент явно ушёл, обращение закрывается без отправки ему ответа.
- learned-answers.md автоматически пополняется вопросом, ответом и временем после ответа владельца (также при уходе клиента). Файл подмешивается в промпт, а перенос в knowledge.md делается вручную. Подтверждения владельца в источнике нет.
- Тихие часы фиксированы: 20:00–09:00 Asia/Jerusalem. Клиентская формулировка: «Уточню у Натали утром, она отвечает с 9:00». Проверка очереди раз в 10 минут; утром вопросы отправляются отдельными сообщениями, чтобы реплеи оставались однозначными.
- Личный номер получателя уведомлений и номер WAHA-сессии вынесены в разные константы natalia.js; отправка идёт только на личный номер. Номер сессии не является адресом эскалаций.
- Промпт требует представляться помощником, говорить о владельце в третьем лице, не использовать угловые скобки. Явных команд паузы бизнеса/диалога в исследованном исходнике не найдено.

## Реализация Леи

- notification_settings повторно используется для тихих часов; добавлены time_zone, owner_phone, owner_chat_id, хеш и срок одноразового подтверждения, auto_replies_paused. tenants.phone не используется как адрес эскалаций. Номер сессии остаётся в whatsapp_instances/SessionStatus.me.
- Отдельный шаг /onboarding/owner после успешного QR-подключения запрашивает номер владельца и тихие часы. Для нового подключения IANA-часовой пояс предлагается по устройству, владелец проверяет/меняет его в настройках; фиксированного Иерусалима в Лее нет. Сервер проверяет отличие от активного номера сессии. Одноразовая команда связывает входящий LID владельца без попыток резолва в телефон. Команда живёт 30 минут; хранится только SHA-256, не код. Клиентам базы хеш недоступен. При смене номера/настроек подтверждение повторяется.
- Браузер вызывает /api/owner-settings в Next.js; прокси проверяет Supabase Auth и owner/admin, сам получает tenant_id из tenant_users. Бэкенд использует существующий admin Bearer middleware, /api/admin/owner-settings GET/POST. В клиентском теле нет доверенного tenant_id.
- Новая таблица escalations нужна вместо неструктурированных agent_actions: отдельный статус обращения, точная связь вопроса/ответа, состояние подтверждения и атомарное обучение. scheduled_jobs остаётся очередью отправки, conversations получает bot_paused. Таблица work_items не задействована: в исходной схеме она зарезервирована для будущих модулей.
- Клиентский ключ (включая полный @lid) сохраняется без изменения. Имя берётся из _data.Info.PushName. Вопросы владельцу отправляются отдельно. Составной ID нормализуется в сервисе, WAHA-провайдер не изменён.
- FAQ-поиск остаётся точным. Gemini может ответить по существующей базе; если сведений нет, возвращает служебный NO_KNOWLEDGE_ANSWER, который не показывается клиенту, а запускает эскалацию. Пустая база/отключённый Gemini тоже ведут к эскалации. Промпт закрепляет роль ассистента; клиентские ответы очищаются от угловых скобок и таких плейсхолдеров.
- Формулировка адаптирована: ассистент уточнит после тихих часов и напишет, когда получит ответ. Дата/час считаются в часовом поясе владельца. Если clients.time_zone известен, сообщение показывает эквивалент в местном времени клиента; иначе явно указывает пояс и время владельца. Есть he/en варианты. WhatsApp не даёт надёжной геолокации клиента, она не угадывается из номера. Клиент может сообщить «Часовой пояс Europe/Berlin», «Timezone Europe/Berlin» или «אזור זמן Europe/Berlin»; сохраняется валидный IANA-пояс и показывается пересчитанное время.
- Только ответ подтверждённого владельца на конкретный вопрос может быть доставлен клиенту. «Позже», «завтра отвечу», «занята сейчас» и подобные явные отсрочки оставляют pending. В отличие от chef-bot, здесь это детерминированная проверка распространённых формулировок, без отдельного вызова Gemini и без автоматических напоминаний. Владелец отвечает позже реплеем на тот же вопрос.
- Закрытие: pending → delivering → delivered только после успешного sendMessage с непустым ID. Это подтверждение отправки транспортом, не отметка о прочтении или физической доставке на телефон: текущий интерфейс провайдера не предоставляет delivery receipts. Ошибка/неопределённый результат → delivery_uncertain, без автоматического повтора и без обучения. Обращение остаётся незакрытым.
- Если язык ответа владельца отличается от языка вопроса клиента, существующий AIProvider переводит только ответ, без дополнения фактами. При недоступности Gemini пересылается оригинал; в базе знаний остаётся оригинальный ответ владельца.
- После отправки владелец видит вопрос и ответ и отдельное предложение сохранить. Только «Да»/«Сохранить»/yes/כן реплеем на этот запрос вызывает атомарную confirm_escalation_learning. Повтор не создаёт дубль; «Нет» отменяет, молчание ничего не сохраняет. Запись knowledge_items: tenant_id, type=faq, question, answer, language, active=true, source=owner_confirmed.
- Все бизнес-запросы новых сервисов привязаны к tenant_id. Операционная таблица escalations и настройки имеют RLS; участники читают только свой tenant, изменения и секрет подтверждения доступны только серверу. Составной FK запрещает связь обращения с диалогом другого tenant. Функция обучения SECURITY INVOKER и доступна только service_role.

## Команды владельца в личном чате с бизнес-номером

- «Пауза всё» / «Продолжить всё» — остановка/возобновление автоответов бизнеса.
- Реплеем на вопрос: «Беру на себя» или «Пауза» — замолчать в диалоге; «Продолжить» — возобновить.
- «Диалоги» — последние 20 активных диалогов с готовыми командами «Пауза диалог …» / «Продолжить диалог …». Можно остановить и диалог без эскалации.
- Глобальное возобновление не снимает ручную паузу отдельных диалогов. Команды владельца работают во время паузы; сообщения клиентов сохраняются, FAQ/Gemini/эскалации не запускаются. Ответ владельца во время паузы не закрывает обращение: нужно возобновить и отправить ответ повторно.
- Вступление владельца оформляется явным «Беру на себя». Переписка с клиентом на отдельном личном телефоне владельца недоступна вебхуку бизнес-сессии; автоматически обнаружить её невозможно без изменения архитектуры/ограничений.

## Очередь и эксплуатация

После запуска backend сервер каждые 60 секунд проверяет scheduled_jobs. Тихие часы рассчитываются в notification_settings.time_zone, включая переход DST. Условное обновление queued → notifying защищает от параллельной отправки несколькими процессами. Перезапуск сохраняет очередь в БД. На момент проверки до миграции старых scheduled_jobs/escalation_created в проекте не было.

Неопределённая отправка или авария между отправкой и фиксацией может оставить notifying/delivering/prompting. Такие записи требуют проверки оператором; автоматического повторения неоднозначной отправки нет, чтобы не создавать дубли. Это осознанное ограничение транспорта без идемпотентного send и delivery receipt. Логи содержат ID обращения/tenant/job и тип ошибки, не тексты, телефоны или секреты.

Allowlist сохраняется без исключений: нужны разрешённые клиент и владелец; неразрешимый @lid при включённом allowlist по-прежнему блокируется существующим ранним фильтром.

SQL: supabase/migrations/20260908075451_024_owner_escalation_workflow.sql. Новых env нет. Миграция применяется через Supabase MCP apply_migration к dorcxwsifrjghdtzkfqv; результат и проверка схемы фиксируются в отчёте задачи. Уже существующим тенантам надо пройти /onboarding/owner: телефон не выводится автоматически из бизнес-номера.

Проверки: npm install, npm run build, npm run typecheck, npm test. Тесты включают полный GOWS webhook до ответа владельца, short-ID, паузы, очередь/DST/конкуренцию, ошибку доставки, подтверждение без дублей и реальное исполнение SQL/RLS в PGlite.
